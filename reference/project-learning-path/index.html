一、项目架构总览

1.1 项目概述

录智是一款中国版 Screen Studio，核心功能是录屏 + AI 美化。项目采用 Tauri 2.0 + React + Rust 技术栈，实现跨平台（macOS/Windows）的屏幕录制、音频采集、光标美化、空白段裁剪和视频导出功能。

二、Rust 语言进阶与工程实践

2.1 并发与同步机制

知识点：Arc<Mutex<T>> 共享状态

源码定位 src-tauri/src/lib.rs:82-94

#[derive(Clone)]
struct AppState {
    service: Arc<Mutex<MacRecordingService>>,
    capture_config: Arc<Mutex<CaptureConfig>>,
    audio_config: Arc<Mutex<AudioConfig>>,
    tick_runtime: Arc<Mutex<Option<TickRuntime>>>,
    beautify_config: Arc<Mutex<BeautifyConfigPayload>>,
    beautify_revision: Arc<AtomicU64>,
    export_cancel_token: Arc<Mutex<Option<Arc<AtomicBool>>>>,
    library: Arc<Mutex<RecordingLibrary>>,
}

源码意图：Tauri 状态管理要求 Send + Sync + 'static，使用 Arc<Mutex<T>> 实现跨线程共享。

⚠️ 源码中的潜在风险
  • 多层嵌套的 Arc<Mutex<...>> 增加死锁风险
  • 锁的获取顺序不一致可能导致死锁
  • .lock().map_err(|_| "锁已损坏") 错误处理过于简单
✅ 最佳实践建议
  • 考虑使用 tokio::sync::RwLock 替代 Mutex 提升并发性能
  • 明确锁的获取顺序，文档化锁的层级关系
  • 使用 parking_lot::Mutex 获得更好的性能和更简洁的 API
  • 对于简单计数器，AtomicU64 是正确选择（源码已使用）
知识点：AtomicU64 原子操作

源码定位 src-tauri/src/lib.rs:91

beautify_revision: Arc<AtomicU64>,

源码意图：使用原子操作实现无锁的版本号递增，用于检测配置变更。

✅ 最佳实践建议
  • 对于版本号递增，Ordering::Relaxed 通常足够
  • 对于需要可见性保证的场景，使用 Ordering::Acquire/Release
  • 参考：Rust 官方文档

    capacity: usize,
    source: &'static str,

    // ...
}

impl<T> MediaSender<T> {
    pub fn try_send_drop_newest(&self, item: T) -> bool {
        match self.inner.try_send(item) {
            Ok(()) => true,
            Err(TrySendError::Full(_)) | Err(TrySendError::Disconnected(_)) => {
                let count = self.dropped.fetch_add(1, Ordering::Relaxed) + 1;
                // 丢弃最新帧，记录丢弃计数
                false
            }
        }
    }
}

源码意图：使用 std::sync::mpsc::sync_channel 实现有界通道，当队列满时丢弃最新帧（Drop Newest 策略）。

⚠️ 源码中的潜在风险
  • 使用标准库 sync_channel，性能不如 crossbeam 或 flume
  • 丢弃策略可能丢失关键帧
✅ 最佳实践建议
  • 考虑使用 crossbeam::channel 获得更好的性能
  • 视频通道容量 90 帧（3秒@30fps）是合理选择
  • 音频通道容量 256 帧，适合音频处理特性
  • 丢弃计数日志每 100 次输出一次，避免日志洪泛（源码已实现）

  • 支持从 Failed 状态重新开始，提升用户体验

3.4 Tauri 异步运行时

知识点：async_runtime 与 spawn_blocking

源码定位 src-tauri/src/lib.rs:318-347

#[tauri::command]
async fn start_recording(app: AppHandle, state: tauri::State<'_, AppState>) -> Result<(), String> {
    let service = state.service.clone();

    let new_state = tauri::async_runtime::spawn_blocking(move || {
        let mut service = service.lock().map_err(|_| "录制服务锁已损坏".to_string())?;
        service.start(config, audio_config, beautify_snapshot, cursor_main_thread_dispatcher)
            .map_err(|e| e.to_string())?;
        Ok::<_, String>(service.state())
    })
    .await
    .map_err(|e| format!("启动录制任务失败: {e}"))??;

    emit_state_changed(&app, new_state);
    Ok(())
}

源码意图：将阻塞操作（如锁获取、录制启动）放到 spawn_blocking 线程池，避免阻塞 Tauri 异步运行时。

⚠️ 常见错误
  • 在异步命令中直接调用阻塞操作（如 lock()）
  • 在 spawn_blocking 中使用 tauri::State
  • 忘记处理 JoinError
✅ 最佳实践
  • 先 clone 状态，再 spawn_blocking
  • 使用 ?? 处理双重 Result（JoinError + 业务错误）
  • CPU 密集型任务使用 spawn_blocking
  • IO 密集型任务使用 tokio::spawn

        duration_nanos: u64,
    ) -> Result<CutTimeline, AppError> {
        // 音频 RMS 静音 + 画面帧差分低变化 + 持续时间超过阈值 = 候选空白段
    }
}

源码意图：结合音频和视频信号检测空白段，避免误剪。

⚠️ 检测策略
  • 音频 RMS：500-1000ms 滑动窗口，保守阈值
  • 帧差分：低分辨率灰度图，计算相邻帧变化率
  • 时间窗口：小于 2 秒不裁剪，5-8 秒才进入候选
  • 缓冲保护：候选段前后保留 300-500ms
  • 保守策略：默认只生成建议时间线，保留原始素材

4.6 FFmpeg 封装

知识点：FFmpeg C API Binding

源码定位 src-tauri/src/media/ffmpeg_writer.rs

// Cargo.toml
[dependencies]
ffmpeg-next = { version = "7", optional = true }

[features]
ffmpeg = ["dep:ffmpeg-next"]

源码意图：使用 ffmpeg-next crate 封装 FFmpeg C API，禁止直接调用 CLI。

🔴 安全约束
  • FFmpeg 命令行参数严禁直接拼接用户输入，防止命令注入
  • 必须使用结构化参数传递
  • 编码任务运行在独立线程，进度通过事件上报
  • 导出失败返回结构化错误

// Cargo.toml

objc2 = "0.6"

🔴 FFI 安全审查要点
  • ObjC 对象的生命周期管理（retain/release）
  • 回调函数的线程安全性
  • 内存泄漏检测
  • 异常处理（ObjC exception → Rust panic）
  • ⚠️ 人工审查点：objc2 系列 crate 版本兼容性

5.3 学习建议

✅ 高效学习方法
  • 先跑通再深入：先用 cargo tauri dev 启动项目，体验完整流程
  • 从测试入手：阅读 #[cfg(test)] mod tests 理解预期行为
  • 关注 TODO/FIXME：搜索代码中的 TODO 和 FIXME，了解待解决问题
  • 对比架构文档：将源码实现与 docs/architecture/ 中的设计文档对比
  • 动手修改：尝试修改参数（如帧率、通道容量），观察行为变化
⚠️ 常见陷阱
  • 不要盲目复制代码：源码中可能存在非最佳实践，需要批判性吸收
  • 注意平台差异：macOS 和 Windows 的实现差异很大
  • 理解生命周期：FFI 代码中的对象生命周期管理是难点
  • 性能敏感：音视频处理对性能要求极高，注意避免不必要的拷贝
